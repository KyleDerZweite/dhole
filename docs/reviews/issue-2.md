# Review of issue #2

Reviewed on 2026-09-05. Issue: [Gateway: dynamic model catalog and CPAMP-class observability](https://github.com/KyleDerZweite/dhole/issues/2). The issue had no comments. Local implementation evidence refers to commit `fe18cdbe734da512b6f86f3ba3f479e2d47f758a`, before the concurrent MVP implementation. This is a proposal review, not a claim that the proposed features have shipped.

The useful part of this issue is removing repeated setup and making failures visible. A mandatory catalog service, client plugin, and six new navigation groups would make the user's desired flow harder. The deployable MVP should let a human sign in, connect an execution machine, and let authorized agents work through the installed runtime. Gateway administration and richer observability should remain optional modules. Core must start with every optional module disabled. Modules may declare dependencies on other modules.

Use the runtime's native catalog when it covers the installed configuration. Add an observed Gateway catalog when it gives the user information that the runtime cannot provide. A client projection is useful only for a client that demonstrably needs it. These are separate reasons to build software.

## Corrections that change the implementation

1. **Codex already discovers models, but not for every authentication configuration.** The current app-server offers `model/list`, including pagination, hidden models, reasoning efforts, and other model metadata. Its native model manager calls `/models?client_version=...`, maintains a cache, and tracks ETags. However, the inspected refresh gate is `uses_codex_backend() || has_command_auth()`. An ordinary custom provider using a static API key does not, by that fact alone, satisfy this gate. Prefer native discovery and fixture-test the intended configuration. Do not claim that every custom endpoint refreshes automatically. `model_catalog_json` is also a supported local configuration field, but a generated file needs an explicit refresh owner and remains a derived copy. See U3 and U4.

2. **The two CLIProxyAPI response shapes are real.** `/v1/models` returns an OpenAI `data` array. Presence of the `client_version` query key selects the Codex response builder, which returns richer metadata. That metadata can include upstream templates and synthesized declarations. A listed model is advertised, not proven callable with a particular account, runtime, tool protocol, or quota state. Record the CPA version, request shape, requested client version, and sanitized credential scope with the observation. See U1.

3. **Catalog authentication is not management authentication.** `/v1/models` runs behind the inference API's authentication middleware. Management routes use a separate management key. The existing Dhole `fetchManagement` helper sends the management bearer and must not be reused unchanged for model discovery. Prefer an existing server-side provider secret reference or a dedicated encrypted catalog credential. Never obtain a browser-visible key by returning `/config` or `/api-key-usage`. See D1, U1, U2, and U8.

4. **Dhole policy cannot enforce calls made directly to CPA.** An effective catalog can control what Dhole and cooperating clients display or select. A client can still submit an arbitrary model ID directly to CPA unless CPA independently enforces that policy. Describe this as Dhole selection policy. Do not advertise an inference authorization guarantee. A removal must disappear from current selection while remaining in immutable history.

5. **A queue lease does not make CPA collection lossless.** The HTTP usage-queue handler calls `PopOldest(count)` before writing its response. There is no acknowledgment, replay cursor, or atomic handoff to Dhole. A timeout, malformed record, process crash, or failed SQLite commit can lose already-popped data. A local lease coordinates only cooperating Dhole workers; it does not coordinate CPAMP or another client. Current Dhole allows a signed-in member to request this path through `sync?includeUsageQueue=true`. Remove or reject that path for the safe MVP. Importing a retained source file is a better baseline. See D1 and U5.

6. **CPA's subscription is also not a durable replacement.** Native RESP `SUBSCRIBE` exists. In the inspected implementation, delivery to subscribers suppresses queue retention. Subscriber buffers hold 256 messages; overflow closes the subscriber. The queue itself is in memory, with a default 60-second retention and a maximum setting of 3,600 seconds. Subscription has no replay cursor or acknowledgment. It can interfere with a queue consumer and cannot supply the issue's durable collection guarantee. A future producer must retain events until acknowledged, or expose durable replay, before Dhole promises complete history. See U6. CPAMP's durable storage begins after receipt; it cannot restore upstream events that never reached it. See U7.

7. **There is some non-destructive usage metadata, not a complete historical export.** `/api-key-usage` provides recent in-memory request counters. Its JSON object keys contain `base_url|api_key`, including the actual key. A generic recursive redactor that only inspects field names is insufficient. Reject raw passthrough and normalize only explicitly permitted fields into opaque identities. The existing statement that CPA has no aggregate usage endpoint is too broad; it lacks the durable, detailed replay interface this issue needs. See U8.

8. **Account status, quota evidence, and scheduler cooldown are different facts.** CPA's auth-file list includes status, account indexes, recent counters, and passive provider quota observations. The inspected quota serializer deliberately excludes scheduler cooldown fields. Missing windows, reset times, or cooldowns must remain unknown. Do not turn an available account row into a claim that a requested model has capacity. Avoid downloading auth files to populate a status screen. See U9.

9. **OAuth exists upstream; the work is safely integrating it.** CPA offers provider-specific auth URL, status, callback, and cancellation routes. These can start browser or device flows; one generic flow cannot be assumed for every provider. Dhole should bind state to the authenticated administrator, keep credentials on the server, bound polling, validate callback inputs, and show expiry or provider errors. Reuse an execution machine's already authorized runtime where possible. Provider consent or an expired credential can still require the human; “one sign-in” cannot eliminate a provider's authentication requirements. See U2 and U10.

10. **An ETag made by Dhole is not upstream compare-and-swap.** CPA's raw YAML writer validates and writes under its own process mutex. The inspected handler has no `If-Match` precondition. Dhole can reject concurrent edits made through Dhole, but a read-check-write sequence cannot eliminate races with another management client. Do not promise race-free multi-writer editing. Defer raw configuration editing or constrain ownership explicitly. Restoring a sanitized diff cannot restore omitted credentials, and restoring an old Dhole secret envelope cannot reactivate a credential revoked upstream. See U11.

11. **Several baseline claims need narrower wording.** Dhole has provider create/read/update and secret rotation, but no provider delete route at the reviewed commit, so “CRUD” overstates it. Its model probe route records administrator-submitted evidence with `verified: false`; it does not perform a live capability measurement. Import can overwrite an existing model's enabled flag. Gateway health returns a generically redacted upstream body, and the same redactor truncates arrays to 100 entries. Catalog parsing must validate the full bounded input before deliberate metadata normalization; silent truncation would invent removals. See D1 and D2.

12. **A discovered model and an enabled model must remain distinct.** Acceptance criteria 1 and 3 are compatible only if a new model appears in the discovered view but remains absent from the effective catalog until enabled. A failed refresh must not look like a valid empty catalog. An effective response's ETag must account for policy and the freshness representation, not only the upstream model hash; otherwise conditional requests can conceal a stale transition.

## How to read the ratings

Value is the benefit for this user's stated workflow, from 1 to 5. Effort is relative to the reviewed code: S is one bounded change, M crosses a few existing boundaries, and L needs a new durable workflow or substantial integration. It is not a delivery estimate. Confidence H means inspected local code or authoritative upstream source establishes the relevant facts. M means the product benefit or compatibility still needs a user workflow or version-specific fixture. L means the necessary upstream guarantee is absent or unverified.

MVP means required for a usable deployment, or required for safety when the optional Gateway/catalog feature is included. It does not mean Gateway is a Core dependency. Next means a deliberate deferral to carry into `ROADMAP.md`. Reject means do not implement the proposal in its stated form; the acceptance cell names a smaller or factual replacement. Repeated ideas retain separate issue identifiers so every checklist item is traceable.

The evidence key at the end links to inspected local files and immutable upstream revisions. Dependencies refer to row IDs below.
